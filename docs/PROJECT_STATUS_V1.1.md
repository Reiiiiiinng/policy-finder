## V1.0 基础能力

以下能力在 V1.0 已交付，V1.1 一个都没有删改：

- 家庭协助模式（操作者 ≠ 受益人）
- 政策主动发现流程（确认情况 → 发现可能相关政策 → 查看政策依据 → 进一步确认）
- 政策证据链（依据什么 / 要求什么 / 出自哪里）
- validity 政策时效与 threshold_signal 阈值提示
- 三层条件模型（资格条件 / 阈值 / 结果参数）
- 佛山政策库接入
- 年龄不确定表达解析（如「70多岁」）
- 生活场景关键词增强
- 结果分层展示（优先关注 / 其他可能相关）与展示减负
- 结果状态：可能相关 / 待确认；明确不符合的政策不进入结果集

## V1.1 新增内容

### 1. 地区隔离：region 正式数据门禁

- 引擎在 `backend/policy_engine.py` 中按 `policy["region"]["scope"]` 做地区比较，
  地区不符一律排除（比较前做「市」后缀归一化）。
- 该门禁此前因为部分政策缺 `region` 字段而形同放行；V1.1 补齐数据后门禁恢复生效。
- 地区判断以政策库正式数据为唯一依据，前端不再有任何名称映射兜底。
- 验收实测：广州用户命中佛山场景词时，佛山库由修复前的 5 条误推降为 0 条；
  佛山用户正常召回 5 条，无回归。

### 2. 前端城市硬编码清理

- 页面文案里的「广州市 / 广州」不再写死；城市名取自 `/api/policies` 每条政策的
  `region` 字段（站点上下文 `SITE`）。
- 接口不可用时退回默认值，保证页面在任何情况下都能正常渲染，V1.0 行为不变。
- 演示案例按政策库覆盖城市切换（广州案例与 V1.0 逐字一致，不破坏既有 Demo）。
- 首页页脚不再写死城市与部门，改为由政策库数据生成。

### 3. AI 理解页局部刷新状态条

- 首次匹配仍保留原有 `renderAiFlow` 四步真实流程（每一步对应一次真实请求），
  **没有**改成简单 loading。
- 新增确认台局部刷新的「进行中」窄条：固定定位、不参与文档流，因此不改变页面高度，
  不影响既有的「局部刷新锁高」与「返回后恢复滚动位置」两套逻辑。
- 文案明确告知「下方仍是上一次结果，更新后会自动替换」，避免用户对着过期结果判断。
- 完成或请求失败均会收起状态条，不残留错误状态。

### 4. 佛山政策库 region 完善

- `data/foshan_medical_assistance_v1.json` 6 条政策全部补齐 `region{scope, level}`。
- `docs/policy-data-spec.md` 把 `region` 标为必填，并写明「缺失会让该政策对任何地区都放行」。

## 当前已知非阻塞问题

以下问题已确认，不影响 V1.1 发布，留待后续版本处理：

1. e2e 工具在 Edge 启动失败时可能静默通过
   （断言数为 0 仍输出「总失败 0」并返回退出码 0）。属测试工具可信度问题，不影响线上产品。
2. 多城市库下 `SITE.region` 采用众数推导，若政策库混合多个城市会取到错误主城。
   当前广州库、佛山库各自单一城市，暂不触发。
3. `fs_med_002` 是省级文件，`region.scope` 标为佛山市。在佛山库语境下是安全收窄，
   但口径需要在后续多城市扩展时明确登记。

## 产品红线（V1.0 / V1.1 共同遵守）

- 系统不判定资格，只输出「可能相关 / 待确认」。
- 禁止输出：你符合资格 / 你一定可以领取 / AI 审核通过 / 系统已自动办理。
- 未知条件一律转入「待确认」，不猜测、不补默认值。
- 不编造政策：名称、部门、条件、流程、金额一律以官方公开文件为准。
- 金额类信息不入库，只引导用户向主管部门核实本人适用标准。
- 操作者 ≠ 受益人，关键信息需受益人确认。

## 后续开发原则

所有修改遵循：

V1.1 稳定版本
        ↓
V1.1.x 小修复
        ↓
V1.2 功能优化

必须遵守：

- 不破坏 V1.0 / V1.1 已有功能与上述产品红线
- 不直接修改 main
- 新功能使用独立分支
- 改动前先检查现有实现
- 不引入未经验证的政策数据
- 不把 AI 输出包装成资格认定

不要：

- 重写匹配引擎
- 修改核心资格判断逻辑（三值判断：未知 → 待确认，明确不符合 → 不推荐）
- 删除已有功能
- 引入未经确认的大规模架构调整

## 后续方向
