# 政策数据规范（政策台账 · 数据字典）

版本：v1.0
建立日期：2026-10-03
适用对象：`data/` 下所有政策库、`backend/policy_engine.py`、政策详情页展示层
性质：**数据层与引擎的共同契约**。新增或修改任何政策，先读本文件。

---

## 一、三层数字模型（核心）

### 1.1 判定规则

> **这个数字如果变了，会改变「用户是否符合」的结论吗？**
> - **会** → 它是**判定依据**，必须入库
> - **不会，只改变「能拿多少」** → 它是**结果参数**，不入库

划线依据是**用途**，不是形式。

### 1.2 为什么不能按「形式」划线

反例：报销比例与起付线是**同一种东西**——都随地区、年度、参保类型变化的具体数字。

- 一级医院报 90%、三级报 80%，地区不同比例就不同
- 起付线 1.2 万元，年度调整就变

风险性质完全一样。若按形式划线，会得到「90% 可以写、1.2 万不能写」这种自己都解释不清的规则，做下去一定会在某条政策上卡住。

### 1.3 三层结构

| 层 | 定义 | 包含内容 | 入库 | 页面输出 |
| --- | --- | --- | --- | --- |
| **第 1 层｜资格条件** | 决定用户是否符合 | 参保状态、病种是否在目录、定点机构、转诊要求、家庭经济认定 | ✅ 参与判定 | 「符合」/「需进一步确认」 |
| **第 2 层｜阈值** | 决定用户是否触及门槛 | 起付线、封顶线 | ✅ 仅内部计算，页面**不显示数值** | 「你可能已触及门槛，具体标准请向医保部门核实」 |
| **第 3 层｜结果参数** | 只决定用户能拿多少 | 报销比例、救助比例、任何金额结果 | ❌ 不入库，不做承诺 | 「具体比例与金额以医保部门核算为准」 |

### 1.4 输入输出边界（不可越过）

- ✅ **内部**：拿用户自述的自付金额与起付线做比较
- ✅ **输出**：「你可能已触及大病保险门槛，建议向医保部门核实具体标准」
- ❌ **绝不输出**：「你符合，能报 X 元」

这仍然是「初步匹配」，没有变成最终裁判。

### 1.5 为什么起付线必须入库

若起付线不入库，系统就无法判断「用户的自付是否触及门槛」——它只能说「请你自己确认是否达到起付线」。而用户本来就是因为不懂才来的。

产品会退化为「清单 + 提醒」，**主动权益匹配这一核心创新直接失效**。

### 1.6 为什么比例必须出去

因为**「可报销 90%」比不给数字更危险**。

用户拿 8 万元自付去乘 90%，期望值算错，实际核算下来是 65%——这种落差对公共服务产品的信任伤害极大。给一个模糊的「以医保部门核算为准」，比给一个会错的数字更负责。

### 1.7 唯一例外（按用途划线的收益）

若某政策**本身以比例为条件**，例如「个人自付占家庭年收入比例超过 30%」，则该比例是**条件**，归第 1 层，入库。

按形式划线会漏掉这种情况；按用途划线自动处理。

## 二、validity 结构（政策时效）

### 2.1 完整结构

```json
"validity": {
  "effective_from": "2025-04-01",
  "expires_at": "2030-03-31",
  "status": "active",
  "superseded_by": null,
  "verified_at": "2026-10-03"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `effective_from` | date \| null | 施行日期 |
| `expires_at` | date \| null | 失效日期；政策未写明时为 `null` |
| `status` | enum | `active` / `expiring` / `expired` / `superseded` |
| `superseded_by` | object \| null | 被哪份新文件替代，含 `name` 与 `document_no` |
| `verified_at` | date | **最后一次人工核对官网的日期** |

### 2.2 为什么需要 `verified_at`（最重要，也最容易漏）

政策可能**没有写失效日期，却已经被新文件悄悄替代了**。`expires_at` 抓不到这种情况，`verified_at` 能。

它同时直接服务于产品的可信度核心——「官方依据」。当被问到「你怎么保证这些政策是准的」，标准答案是：

> 每条政策都有最后核对日期，且链接到政府官网原文。

### 2.3 为什么需要 `superseded_by` 与四态

不要只有「有效 / 失效」两态。**已失效的政策不要静默删除**：

- 静默删除 → 用户以为自己记错了 / 从来没这条政策（信息黑洞）
- 显式替换 → 「该政策已由 XXX 文件替代」+ 给新文件入口（可信度展示）

### 2.4 页面文案三档

| status | 页面文案 | 视觉 |
| --- | --- | --- |
| `active` | 依据：《XX 办法》（X医保规〔2023〕X号）· 最后核对 2026-10-03 | 无标记 |
| `expiring` | 本办法有效期至 YYYY-MM-DD，届时请以最新文件为准 | ⚠️ 橙色提示 |
| `expired` / `superseded` | 该政策已由 XXX 文件替代 → 查看新规 | 灰显 + 跳转入口 |

**注意**：「即将到期」用 ⚠️ 不用 ❌——它仍是有效政策，只是有期限。

`expiring` 的判定：`expires_at` 距今不足 180 天，由引擎按当天日期计算，**不写死在数据里**。

## 三、规模边界声明（必须写进产品文档）

比赛阶段只有 3–5 条政策，人工维护可行。规模扩大后需建立定期复核机制：

- 按 `verified_at` 排序的**自动巡检队列**
- 对 `status = expiring` 的文件提前预警
- 对 `superseded` 关系建立**替代链**，保证新旧文件可追溯

主动把这个问题说出来，比被问住好。

## 四、数据字典

### 4.1 政策顶层字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `policy_id` | string | ✅ | 唯一标识，格式 `<城市缩写>_<领域>_<序号>`，如 `fs_med_001` |
| `policy_name` | string | ✅ | 政策名称，与官方文件标题一致 |
| `policy_level` | string | ✅ | `省级` / `市级` / `商业` |
| `category` | string | ✅ | 救助方向，如 `医疗救助` / `大病保险` / `门诊保障` / `临时救助` / `前置认定` / `商业补充` |
| `target_people` | string[] | ✅ | 面向人群，用**政策原文表述**，不改写 |
| `description` | string | ✅ | 政策说明，以原文为依据 |
| `life_scenes` | string[] | ✅ | 生活场景标签，取自 `scene_tag_library` |
| `conditions` | object | ✅ | 见 4.2（三层模型） |
| `match` | object | ✅ | `scene_signals[]` + `priority`(1 最高) |
| `missing_information` | string[] | ✅ | 需要用户或受理单位确认的信息 |
| `ai_reason` | string[] | ✅ | 政策侧表述，支持 `{who}` `{age}` `{region}` 占位符 |
| `scene_reason_map` | object | — | **仅当对应场景被识别时**才生成的推荐理由 |
| `application_process` | object[] | ✅ | `{step, to_verify}` |
| `materials` | object[] | — | 收件清单，须标注出处条文；无原文依据时留空并置 `to_verify` |
| `source` | object | ✅ | 见 4.3 |
| `validity` | object | ✅ | 见第二节 |
| `verification` | object | ✅ | `{status: verified\|to_verify, checked_at, note}` |
| `risk_notice` | string | ✅ | 免责表述 |
| `keywords` | string[] | — | 检索关键词 |
| `green_note` | object | — | 节约型公共服务说明，见第五节 |

### 4.2 conditions（三层模型落库格式）

```json
"conditions": {
  "qualify": [
    {
      "key": "insurance",
      "type": "boolean",
      "label": "参加本市基本医疗保险",
      "requirement": "已参加佛山市基本医疗保险",
      "source_ref": "佛医保〔2025〕13号 第九条"
    },
    {
      "key": "family_economic",
      "type": "enum",
      "label": "家庭经济状况认定",
      "options": [
        { "value": "tekun",       "label": "特困人员" },
        { "value": "di_bao",      "label": "最低生活保障对象" },
        { "value": "di_bao_bian", "label": "最低生活保障边缘家庭成员" },
        { "value": "zhi_chu_xing","label": "支出型困难家庭成员" },
        { "value": "none",        "label": "以上都不是" }
      ],
      "source_ref": "佛医保〔2025〕13号 第六条"
    }
  ],
  "thresholds": [
    {
      "key": "deductible",
      "label": "年度救助起付标准",
      "value": 12000,
      "unit": "元/年",
      "applies_to": ["zhi_chu_xing"],
      "source_ref": "佛医保〔2025〕13号 第十一条"
    }
  ],
  "result_params": {
    "has_ratio": true,
    "has_amount": true,
    "note": "报销比例与救助金额为结果参数，按规范不入库、不展示数值"
  }
}
```

**硬性约定**

1. `qualify` 里的每一项都必须能被用户**自判**（是 / 否 / 不确定），或从有限选项中选出。不能自判的条件不入 `qualify`，改写进 `missing_information`。
2. `thresholds` 的 `value` **只用于内部比较**，任何页面渲染路径都不得直接输出该数值。
3. `result_params` 只声明「存在比例 / 金额」，**不存数值**。
4. 每一条条件、阈值都必须带 `source_ref`，精确到条款号。核不到原文的，整条不写。

### 4.3 source

```json
"source": {
  "department": "佛山市医疗保障局等五部门",
  "document": "佛山市医疗救助实施办法",
  "document_no": "佛医保〔2025〕13号",
  "publish_date": "2025-02-28",
  "official_url": "https://www.foshan.gov.cn/gfxwj/sbmgfxwj/fssylbzj/content/post_6274174.html"
}
```

`document` 为 `to_verify` 时，`document_no` / `official_url` 一律留空，页面显示「来源待核验」。

### 4.4 画像侧新增字段

为支撑第 2 层阈值的内部比较，`profile` 增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `self_paid_amount` | number \| null | 用户自述的、经基本医保与大病保险支付后个人负担的合规医疗费用（元） |
| `family_economic` | string \| null | 家庭经济状况认定类别，取值见 `conditions.qualify[].options` |

`self_paid_amount` **只用于与阈值比较**，不参与任何金额计算，不对外输出。

## 五、绿色价值字段（节约型公共服务）

每条政策可声明 `green_note`，用于「这项服务省掉了什么」模块。**必须引用官方原文，不自行表述**。

```json
"green_note": {
  "anchors": ["少跑动", "一次性告知"],
  "citations": [
    {
      "point": "材料不齐全时一次性告知全部补正内容",
      "text": "对材料不齐全或不符合要求的，应一次性告知申请人所需补正的全部内容。",
      "source_ref": "佛民办〔2021〕98号 第十一条"
    }
  ],
  "disclaimer": "本条为政策原文的流程性说明，不构成任何碳减排量化承诺。"
}
```

`anchors` 取值限定为：`无纸化` / `少跑动` / `一次性告知`。

## 六、维护约定

1. **改动数据前先读本规范**；新增字段需同步更新本文件第四节。
2. **政策台账与数据层是同一份东西**：填写政策时同时填 `validity.verified_at` 与 `validity.superseded_by`，不做两处维护。
3. 每次核对官网后，更新该条政策的 `verified_at`。
4. 修改匹配逻辑后，用 `python .tools/baseline.py save` 更新基线快照，并在 `docs/README.md` 修改记录中说明。
