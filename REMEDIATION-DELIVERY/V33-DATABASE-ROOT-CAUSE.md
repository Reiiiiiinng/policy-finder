# V3.3 数据库根因与恢复验收

## 上轮发生了什么

以审计运行记录中的成员、分析和计划 UUID 为键，在历史库中使用 SQLite 只读连接反查。上轮 8164 所谓 live 测试的成员和分析落在 `v33-trip-manual-final`。8165 的三个 Edge 运行的成员、分析和计划全部落在 `v33-trip-final-extra`。这些记录均未出现在启动日志声称的新审计库。两处是 SQLite 主文件，当前均为回滚日志 delete 模式，未见 WAL、SHM 或热回滚日志，业务时间与文件写入时间相符。可重现的证据是 UUID 反查；请求究竟在哪一层被路由到历史服务、历史进程 PID 和所有者仍待确认。没有覆盖或恢复历史文件。本轮前后两个历史库 SHA-256 相同。

## 实施的修复

- `preview.py` 要求显式预备数据库。启动时固定解析路径，拒绝不存在的文件、指向其他路径的链接和硬链接；在整个服务期持有实例文件的 OS 锁。
- `followup_db.py` 把预览进程默认连接固定到启动文件，继续使用 SQLite `mode=rw` 请求写入与显式事务提交。预检校验 schema、版本、数据库头、完整性与外键。
- 预览启动时用生成的实例运行标识校验自己的 loopback 响应，写入需要当前实例的运行标识或由同源 GET 建立的 Cookie。自动化在第一条写入前分别验证 Node 和 Edge 实际响应标识。新端口避免复用历史入口。
- 新库使用 v6。新 schema 为计划增加暂停时间和原因，并新增按账户、成员、查询 UUID 隔离的草稿表。历史 v5 库保持原样。人工启动前必须预备独立库。启动缺失路径时退出。

## 复验



运行在新的 28749 与独立库中。以两项真实目录政策运行替身 AI 和合成家庭。首次以当前可见的「查看计划」按钮复验后发现，草稿 GET 把空演示场景编码成字符串 null，服务端返回 400。省略空参数后重新验证草稿回读。计划重启测试以 API 完整对象和只读文件为证据。条件核对通过集中核对持久化，材料准备值存于任务 JSON 及材料事件。
